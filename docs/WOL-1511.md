# Экономика ручных возвратов и возмещений

Включение: `REFUND_CASES_ENABLED=true`, только после обеих миграций e_com_backend.
По умолчанию расчёты прежние. Исторические кейсы с economics_managed=false не участвуют.

После нативных расчётов YM/WB/Ozon/MM/Sportmaster применяется один слой
`apply_refund_cases`. Этот же слой используется детализацией кейса, API заказа,
Streamlit-таблицами и аналитикой. Исходный expected_profit не переписывается.

Дополнительный расход = проведённые компанией расходы − подтверждённое покрытие
именно этих расходов нативным расчётом. Плановые суммы дают отдельный прогноз.
Покупательские расходы не уменьшают прибыль. Неизвестный FX-эквивалент не считается RUB.
Связь с отчётом проверяется по текущему fingerprint и coverage; при неоднозначности
точная прибыль/actual_profit отсутствуют. Само совпадение даты/суммы не доказывает покрытие.
Для MM customer refund coverage остаётся unknown, пока не доказана связь с формулой,
которая использует конкретную сумму. Принудительно считать такую связь included нельзя.

Товар: уже признанная закупка минус целевая закупка в расходах. Пригодные остатки
восстанавливают стоимость после приёмки; брак и потеря сохраняют стоимость в расходах.
Возмещение без товара сохраняет закупку, даже если нативный статус возврата ранее её убрал.
При пересечении нескольких кейсов одна split-единица корректирует товарную стоимость
один раз, с приоритетом фактического физического результата.

Стоимость — зафиксированный снимок или цепочка первого income и закупки через
v_refund_unit_costs. Источник учитывает существующее правило валюты ru_custom_price.
Положительный плановый fallback помечается after_sales_cost_estimated; неизвестный
или автоматически заполненный ноль не превращается в подтверждённую закупку.
При неоднозначном распределении нативной закупки между частично возвращёнными единицами
результат также остаётся неполным.

Ревизия проверяется при обходе полного API-снимка и входит в Streamlit cache key.
Изменение ревизии во время расчёта не выдаёт точную прибыль. Данные кейса и его результат
используют один финансовый контекст, с повторной проверкой ревизии и отчётных fingerprint.
Кеш имеет минутный bucket для переимпорта платформенных источников без ручных команд.
KPI исключает неполный заказ из суммы точной прибыли и показывает отдельный счётчик.

Проверки: `.venv/bin/python -m pytest -q`. Новые контрольные примеры находятся в
`tests/test_refund_cases.py`. Миграции, preflight и проверка реальных складских триггеров —
в `e_com_backend/docs/WOL-1511.md`. Продакшен-проверку отчётов пяти платформ и пилотную
сверку реальных кейсов выполняют до массового включения; локальные тесты их не заменяют.

## Дополнение 29.10

Новые денежные назначения: стоимость бесплатной замены, возмещение поставщика,
перевозчика и возврат комиссии. Известная стоимость замены — план при резерве и
факт при выдаче; восстановление старого товара независимо. Поступления увеличивают
результат, расходы уменьшают. API дополнительно отдаёт gross expenses/reimbursements
и их планы; совместимое поле after_sales_expense остаётся чистой корректировкой.
Расходы и поступления не показываются одной отрицательной расходной строкой.

Возврат комиссии/возмещение перевозчика требуют доказательства отражения в базовом
отчёте независимо от способа перевода. Пока адаптер такого поступления не доказывает
покрытие, результат needs_reconciliation и точная прибыль отсутствует; сама сумма
известного поступления видна. Заявленная претензия без денежной операции прибыль не
меняет. Для замены с неизвестной стоимостью точная прибыль также отсутствует.
Внешняя приёмка в Китае не восстанавливает собственный складской актив.
